Scroll thumb

A scrollbar for a floating panel that reserves no width: the panel's own right border thickens to report position, and becomes a small sheet when you reach for it. Built for Eafora's detail dock, written up here because the interesting parts are the half-dozen browser behaviours it has to work around, and those are the same in any project.

The shipped code is the definition, not this page. The control lives in web/src/map/scroll_thumb.rs (geometry, drag, wheel) and web/style/components/_detail-panel.scss (the two elements and their states). The CSS below is a faithful copy and the JavaScript is a port of the Rust, so the demo stands alone and can be lifted into another project; if the two ever disagree, the Rust and SCSS win.

Demo

Move the pointer into a panel to raise the thumb, onto the thumb to open it, and drag it. A wheel over the thumb scrolls the panel. The left panel overflows by a little and the right by a lot, which is what changes the thumb's length.

What it is

The constraint that produced it: a scrollbar must not take a column from the panel's text. A reserved gutter shifts every line left by its width, and on a text-dense panel that is the most expensive nine pixels on screen. So the indicator lives on the boundary the panel already draws, and on the ten pixels of map between the panel and the viewport edge, neither of which is anyone's content.

It has three states and a fourth that only a pointer sees:

Pointer outside the panel
Nothing is drawn. A reader who is not scrolling has no use for a scroll position.
Pointer in the panel
A two-pixel bar of ink, centred on the panel's right border, its length proportional to how much of the content is visible and its position to how far down you are.
Pointer on the thumb
Seven pixels wide, opaque white behind one hairline, with circular caps. It becomes a sheet, which is what everything else in this interface is.
Held
The same as hovered, and it stays that way while the drag continues even after the cursor has left the seven pixels, which it will immediately.

The design decisions worth keeping

  • Round caps, in an interface with square corners everywhere else. A cap on a two-pixel bar cannot read as square; at that size the corner is the whole shape. This is the one rounded thing.
  • It grows outward and inward equally, centred on the border, so it never covers a glyph.
  • A margin at both ends of the track, so a thumb at either extreme does not touch the panel's corner.
  • A minimum length. Below about twenty-four pixels a thumb cannot be grabbed, so on very long content it stops being proportional rather than becoming unusable.
  • Two properties animate, and only on the way out. Arriving, the sheet appears at once. Leaving, the width closes and the fill darkens together. Nothing else in the control moves: the thumb's position along the track cuts instantly to wherever the content is.

Implementation, and the parts that fought back

The geometry is four lines of arithmetic. Everything below is a browser behaviour that had to be worked around, in the order they were hit.

Symptom The thumb drew a couple of pixels right of the border, then snapped left at the end of the transition.
Cause transform: translateX(-50%). A percentage inside a transform is resolved once, when the transition starts, so it held the narrow box's offset while the box grew, then jumped when the computed style took over.
Fix Express the offset as a length. Half the box interpolates in step with the width, because box width is linear in the interior width. Or, as here, put the offset on a wrapper whose box never changes, so nothing interpolates at all.
Symptom The thumb appeared instantly on entering the panel but animated on leaving.
Cause The only property changing between absent and present was a hairline border, and a hairline is one pixel or none. There is nothing between to interpolate, so it stepped.
Fix Appearing and disappearing is a horizontal scale, which has a continuous range. Attempting to close the border smoothly instead does not work either: border widths are quantised for rasterisation, so a 1px-to-1.5px animation steps late rather than gliding.
Symptom Entering the panel directly onto the thumb raised it, but it would not open until the pointer moved again.
Cause At scaleX(0) the element has no hit area, and a browser re-tests what is under the pointer only when the pointer moves. Growing under a stationary cursor never fires :hover.
Fix Two elements. A wrapper carries the position and the pointer target and never changes size, so it is hoverable before anything is visible; the bar inside it is the only thing that scales. This is why the control is not one div.
Symptom A visible sideways shimmy on every open and close.
Cause Not layout: the measured centre held to four thousandths of a pixel throughout. The containing panel's width was 27.83rem, or 445.28px, so its right border sat on a fractional pixel and the thumb's hairline rasterised onto a different device pixel from frame to frame as it grew.
Fix Put the container on whole pixels. Any hairline centred on a fractional edge will do this; the control cannot fix it from the inside.
Symptom Closing the thumb ended with a thin white line being erased in a single frame.
Cause The fill changed from white to ink at one instant, and at the moment it changed there was still a sliver of white enclosed by the border.
Fix Two halves. box-sizing: content-box makes width the interior, so closing it to zero lets the two borders meet and squeeze the white out. And the fill darkens over the same span on cubic-bezier(0.7, 0, 0.84, 0), nearly flat at first, so the two finish together.
Symptom A wheel with the pointer over the thumb scrolled nothing.
Cause The thumb is a sibling of the scrolling element, not a child, so a wheel over it has no scrollable ancestor: the panel does not scroll and neither does the page.
Fix Forward the event's deltaY to the scroller the thumb represents, and prevent the default.
Symptom A drag stopped the instant the cursor left the thumb, which was immediately.
Cause Seven pixels is narrower than a hand can hold a straight line.
Fix setPointerCapture on pointerdown, and record where along the thumb the grab landed so the thumb moves with the cursor instead of jumping its top to it.
Symptom A panel whose content fits showed a thumb anyway, but only at some browser zoom levels.
Cause clientHeight and scrollHeight are integers, each rounded from a fractional layout independently, so they can land a pixel apart when nothing actually scrolls.
Fix Treat one pixel of reported overflow as fitting. One is the exact bound: each measurement is off by at most half a pixel, so the spurious difference can never exceed it.
Symptom The thumb was hard to grab.
Cause A two-pixel bar is not a pointer target.
Fix The wrapper is four pixels wider than the bar on each side. Turn on "show the pointer target" above to see it.

The geometry

Two pure functions, tested on their own away from the DOM. length is proportional to the visible fraction with a floor, and top puts it along a track inset at both ends:

const TRACK_MARGIN = 6;      // clear of the panel's corners at either extreme
const MINIMUM_LENGTH = 24;   // below this a thumb cannot be grabbed
const MINIMUM_OVERFLOW = 1;  // a rounded pixel is not overflow

function geometryFor(visibleLength, contentLength, scrollTop) {
    const scrollable = contentLength - visibleLength;
    if (scrollable <= MINIMUM_OVERFLOW) {
        return null;
    }

    const track = visibleLength - 2 * TRACK_MARGIN;
    const length = Math.max(track * visibleLength / contentLength, MINIMUM_LENGTH);
    const travelled = Math.min(Math.max(scrollTop / scrollable, 0), 1);

    return { top: TRACK_MARGIN + travelled * (track - length), length };
}

function scrollTopFor(requestedTop, visibleLength, contentLength, thumbLength) {
    const scrollable = contentLength - visibleLength;
    const travel = visibleLength - 2 * TRACK_MARGIN - thumbLength;
    if (scrollable <= MINIMUM_OVERFLOW || travel <= 0) {
        return null;
    }

    const travelled = Math.min(Math.max((requestedTop - TRACK_MARGIN) / travel, 0), 1);

    return travelled * scrollable;
}

Recompute on scroll, and again when the pointer enters the panel. The second covers a viewport resize without a resize listener, because the thumb cannot be reached without entering the panel first.

What it costs

A browser scrollbar is free because the browser positions it. This is an element the client positions itself from a scroll listener, and it is not reported to assistive technology as a scrollbar. Native keyboard scrolling of the panel is unaffected, since the panel is still a real scrolling element; only the visible indicator is replaced. Firefox is not a special case here, because nothing depends on ::-webkit-scrollbar; the native bar is hidden with scrollbar-width: none, which Firefox does support.
