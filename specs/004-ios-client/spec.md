## Scenarios & Testing *(mandatory)*

### First-paint map render against the embedded bundle on the simulator (P1)

A developer with a fresh `eafora` checkout runs `setup.sh` (which installs the iOS toolchain dependencies — `xcode-select --install`, `brew install xcodegen yq`, `rustup target add aarch64-apple-ios aarch64-apple-ios-sim` — and runs `xcodegen generate` to materialize `ios/Eafora.xcodeproj/`); then opens that project in Xcode and runs the `Eafora` scheme against the iOS Simulator. Xcode's pre-build phases execute in order: `scripts/build/build-ios-xcframework.sh` builds the Rust core into `target/uniffi/EaforaCore.xcframework`; `scripts/build/sync-embedded-bundle.sh` plain-copies the downsampled bundle into `ios/EaforaApp/Resources/embedded_artifacts/`; `scripts/build/inject-git-revision.sh` writes the current git revision into the app's `Info.plist`. The app launches: `EmbeddedBundle.swift` locates the bundled artifact root via `Bundle.main.url(forResource: "embedded_artifacts", withExtension: nil)`, reads the manifest, and constructs a `shared::artifact::Bundle` synchronously before the first frame. The SwiftUI `MapView` mounts; the `MapMTKView` `UIViewRepresentable` brings up an `MTKView` whose `CAMetalLayer` is handed to `EaforaCore.attachSurface(...)`; the first `draw(in:)` callback fires `EaforaCore.drawFrame(...)` and the world map renders in Miller cylindrical projection with the active statistic (TFR) painting the choropleth. The layout matches `docs/design/stub-mobile.html` frame 00 (empty map with choropleth legend and tap prompt at the bottom). This is the deliverable that closes the §Follow-up work item in `docs/architecture/client-ios.md`. Without it, every other iOS feature stays speculative.

**Acceptance Scenarios**:

1. **Given** a fresh checkout on a Mac with Xcode 16+ installed, **When** the developer runs `setup.sh` (which installs the iOS-side toolchain dependencies and runs `xcodegen generate`), opens `ios/Eafora.xcodeproj`, selects an iOS Simulator destination (e.g. iPhone 16 Pro running iOS 18), and presses Cmd-R, **Then** Xcode's pre-build phases run in order (xcframework build → embedded-bundle sync → revision injection), the app builds successfully, and the simulator launches the app to a rendered world map with TFR choropleth coloring within a few seconds of the build completing.
2. **Given** the app has rendered against the embedded bundle on the simulator, **When** the user taps a country polygon, **Then** the region detail bottom sheet presents at the `.medium` detent (per `docs/architecture/client-ios.md` §Navigation structure) showing the region's name + the active statistic's value + the source attribution per `docs/design/stub-mobile.html` frame 01. Tapping the drag indicator and dragging expands to `.large`; dragging down dismisses; the map stays visible behind the sheet.
3. **Given** the map has rendered, **When** the user changes the statistic picker in the controls panel, **Then** the choropleth re-paints synchronously (no animation per `docs/design/README.md` §Animation v1 policy); the MTKView's `setNeedsDisplay()` is the only trigger; no continuous frame loop runs.
4. **Given** the map has rendered with year scrubber at the most-recent year (the only year the embedded bundle ships per `docs/architecture/client.md` §Embedded downsampled artifact), **When** the user drags the scrubber to a year not in the embedded bundle, **Then** that year has no values; the choropleth renders countries-with-no-data as the design vocabulary's "no data" state (white fill); pan and zoom still work.
5. **Given** the app launches without connectivity (Simulator's "Network Link Conditioner" set to 100% loss, or a real device in airplane mode), **When** the launch sequence runs, **Then** the embedded bundle still renders the map normally (it is the offline-capable baseline per `client.md` §Embedded downsampled artifact); the discovery + live-fetch tasks fail silently in the background; the embedded bundle remains the floor.

### File-system cache adapter persistence + iOS purge recovery (P2)

The iOS client's `FileSystemArtifactCache.swift` implements the cross-platform `ArtifactCache` contract against `<app-sandbox>/Library/Caches/artifacts/`. Through this feature the cache adapter is exercised end-to-end against the iOS Simulator's file system via XCTest: a `put` → `get` round-trip returns byte-equal `Data`; a missing key returns `nil`; `deleteVersion` removes a version subtree; `listVersions` enumerates persisted versions; the "keep the current version + the most recent prior version" eviction policy (per `client.md` §Cache eviction) removes older subtrees on startup; directory creation is idempotent (the cache initializes cleanly whether or not `Library/Caches/artifacts/` already exists). The cache adapter sets `NSURLIsExcludedFromBackupKey` on the `artifacts/` directory at first creation per `client-ios.md` §iOS-specific behavior (cache contents are reproducible from the CDN; they don't belong in iCloud / iTunes backup). iOS may purge `Library/Caches/` under storage pressure; when that happens, the embedded bundle is the floor on the next launch and the live fetch path runs as if first launch — no separate recovery code, just the same path P3 already exercises.

**Acceptance Scenarios**:

1. **Given** a freshly-installed simulator app with empty `Library/Caches/`, **When** `cache.put("2026-06-22+ada", "manifest.json", bytes)` runs followed by `cache.get("2026-06-22+ada", "manifest.json")`, **Then** the returned `Data` is byte-equal to the input.
2. **Given** an empty cache, **When** `cache.get("2026-06-22+ada", "manifest.json")` runs, **Then** the result is `Ok(nil)` (Swift: `nil`).
3. **Given** `Library/Caches/artifacts/` holds three version subtrees (`2026-06-01+...`, `2026-06-10+...`, `2026-06-22+...`), **When** the cache initializes at startup and calls `evictOldVersions()`, **Then** `2026-06-01+...` is deleted and the two most recent subtrees remain intact (per `client.md` §Cache eviction).
4. **Given** the `artifacts/` directory does not yet exist when the cache constructor runs, **When** the constructor runs, **Then** the directory is created with `NSURLIsExcludedFromBackupKey` set; a subsequent `cache.put(...)` succeeds without further setup.
5. **Given** the simulator is reset (`xcrun simctl erase booted`) between two test runs — which simulates iOS purging `Library/Caches/` under storage pressure — **When** the app launches a second time, **Then** the embedded bundle renders the map normally (the floor is preserved); subsequent cache operations work without crash; the cache constructor recreates the directory transparently.

### Discovery + speculative parallel fetch + bundle hot-swap (P3)

When the producer side has stood up `https://repository.eafora.org/` and the `latest/manifest.json` pointer (per `docs/architecture/client.md` §Live bundle: stable pointer), the iOS app picks up the live bundle on first launch and on each subsequent launch. The startup sequence per `client.md` §Speculative parallel fetch at startup: the discovery fetch (`https://eafora.org/discovery`) and the speculative manifest fetch (`<baked_repository_base_url>/latest/manifest.json`) fire in parallel via `URLSession`; the embedded bundle has already rendered the map; the Swift fetcher writes verified bytes into `Library/Caches/artifacts/<version_label>/<relative_path>` as each shard verifies; once the manifest + every referenced shard is on disk, Swift calls `eaforaCore.pushBundle(manifestPath: ...)` (path-based handoff, not bytes-across-FFI — per `client-ios.md` §UniFFI surface); Rust opens the manifest, validates every SHA-256 (single source of truth per `client-ios.md` §UniFFI surface), constructs the live `Arc<Bundle>`, and publishes it on the renderer's `tokio::sync::watch::Sender<Arc<Bundle>>`; the next `setNeedsDisplay()`-triggered `draw(in:)` callback paints the live bundle. The visual transition is instant per `docs/design/README.md` §Animation. On a returning visit with a populated cache, the cached live bundle replaces the embedded bundle as the floor for first paint, and the latest-revision check happens in the background. Until the producer-side prerequisites land, the flow is exercised against a same-origin stub: a discovery document at `web/static/discovery` (already shipped by the 003-web-client feature) whose `repository_base_url` points at the web tree's static-asset path; switching to real `repository.eafora.org` is a configuration change, not a code change.

**Acceptance Scenarios**:

1. **Given** a populated `https://repository.eafora.org/` with a `latest/manifest.json` pointing at a version newer than what the embedded bundle ships, **When** a first-launch user opens the app on a real device, **Then** the embedded bundle renders first, the discovery + manifest fetches resolve concurrently, the shards download (concurrency capped at 4 per `client.md` §Stage 3; `URLSessionConfiguration.httpMaximumConnectionsPerHost = 4`), each shard's SHA-256 is verified inside Rust on `pushBundle`, the cache writes through as bytes verify, and the renderer hot-swaps to the live bundle within a few seconds of first paint.
2. **Given** a returning user whose `Library/Caches/artifacts/` holds a live bundle from a prior launch and the producer has not published since, **When** they launch the app, **Then** the cached live bundle renders as the first paint (skipping the embedded bundle as the starting point per `client.md` §Returning-visitor flow); the discovery + latest-manifest fetches still fire; the cached bundle is already current, so no re-download happens.
3. **Given** the discovery fetch fails (offline / 5xx / malformed document) but the speculative manifest fetch succeeds against the baked-in `repository_base_url`, **When** the client reconciles, **Then** the speculative result is used (per `client.md` §Speculative parallel fetch step 4) and the bundle hot-swaps normally; one round trip total.
4. **Given** the discovery fetch reports a `repository_base_url` different from the baked-in fallback (re-platform happened), **When** the client reconciles, **Then** the speculative-fetch result is discarded and a new manifest fetch fires against the discovered URL; the bundle hot-swaps once the new fetch resolves; two round trips total, one wasted.
5. **Given** Rust's `pushBundle` call detects a shard SHA-256 mismatch, **When** the call returns an error, **Then** the Swift fetcher retries once after approx. 100 ms; persistent mismatch surfaces a UI banner; the embedded bundle (or cached live bundle on a returning launch) remains rendered as the floor. The retry loop lives Swift-side per `client-ios.md` §URLSession fetch adapter (the loader inside `shared::artifact` owns the retry policy; the Swift fetcher invokes it).

### TestFlight-ready build + Universal Links (P4)

The owner runs the CI flow on the Mac mini M1 (per `docs/architecture/overview.md` §CI/CD): `xcodegen generate` → `xcodebuild archive` → `xcodebuild -exportArchive` with `destination = upload` in `ExportOptions.plist` → the App Store Connect API key (stored at `$APPSTORE_CONNECT_API_KEY_PATH` per `client-ios.md` §Signing and CI) authenticates the upload. The build lands in App Store Connect's Internal Testing track on TestFlight without manual intervention. The build number monotonically advances from `git rev-list --count master` per merge. Universal Links work end-to-end: tapping `https://eafora.org/region/usa` on a device with the TestFlight build installed opens the app to the USA region detail sheet (not a Safari page); tapping `https://eafora.org/about` opens the app to Settings with About visible at the top. The AASA file at `https://eafora.org/.well-known/apple-app-site-association` is served by the dedicated `tools/aasa-deploy/` Cloudflare Worker (assets-only, no JS handler); the file's `appID` is rendered from `ios/project.yml`'s `TEAM_ID` + `BUNDLE_ID` by `ios/setup.sh` (via `yq`); the deploy happens via `scripts/build/deploy-aasa.sh`.

**Acceptance Scenarios**:

1. **Given** an Apple Developer Program enrollment with valid App Store Connect API key secrets installed in the Mac mini CI environment, **When** the CI workflow runs the archive + export + upload chain, **Then** the build appears in App Store Connect's Internal Testing track within a few minutes; the build number matches `git rev-list --count master`; no manual intervention is needed.
2. **Given** the AASA file deployed at `https://eafora.org/.well-known/apple-app-site-association`, **When** a request hits that URL, **Then** the response is `Content-Type: application/json`; the body is the rendered AASA with `appID = "<TEAM_ID>.<BUNDLE_ID>"` matching `ios/project.yml`; the response is served by the `tools/aasa-deploy/` Worker, not the main web Worker.
3. **Given** the TestFlight build is installed on a real device, **When** the user taps `https://eafora.org/region/usa` (from a Messages app, an email, a QR code, etc.), **Then** the iOS app opens (not Safari); the region detail sheet presents with the USA region selected; the map behind the sheet shows USA as the selected region.
4. **Given** the same device, **When** the user taps `https://eafora.org/about`, **Then** the iOS app opens; the Settings bottom sheet presents; the About section is visible at the top without scrolling.
5. **Given** a fresh device install (no app data), **When** the user opens the app for the first time via launching from the home screen (not via deep link), **Then** the embedded bundle renders the map within a few seconds; the launch-to-first-paint time is under 2 seconds on an iPhone 13 or newer.

### Edge Cases

- **Xcode pre-build phase fails** (e.g. `cargo build --target aarch64-apple-ios --release` errors, or `yq` is missing) — the Xcode build fails with the script's stderr surfaced into Xcode's build log; the app does not launch; the developer fixes the underlying issue. This is the intended failure mode (pre-build phases that fail block the build by design).
- **Dirty working tree at archive time** — `scripts/build/inject-git-revision.sh` writes `<full-sha>-dirty` to `Info.plist`'s `EaforaRevision`. The `-dirty` suffix is the signal that the binary cannot be reproduced from source alone; this is correct for dev builds and a CI-only error condition. For TestFlight / App Store builds, CI MUST fail the build if the working tree is dirty (the source state is what the user will be told they installed; ambiguity is unacceptable).
- **`Library/Caches/` purged mid-session** (iOS reclaims storage while the app is foregrounded) — the in-memory `Arc<Bundle>` keeps the map rendering; the next attempted `cache.put` runs against a fresh directory (created on demand by the cache adapter's idempotent directory-ensure logic); on next launch, the cache is empty and the embedded bundle renders first as if first launch.
- **MTKView's `CAMetalLayer` is recreated** (orientation change, multi-tasking transition, or any UIView lifecycle event that tears down the layer) — the SwiftUI `MapMTKView` `UIViewRepresentable`'s `updateUIView(_:)` or the underlying view-lifecycle hook calls `eaforaCore.detachSurface()` then re-`attachSurface(...)` with the new layer pointer; the renderer's wgpu device + queue + pipeline state survive across the detach/attach cycle (constructed once at `EaforaCore::new` time per `client-ios.md` §Rendering); only the surface itself is reconstructed.
- **App resumed from background after a long pause** — iOS may have torn down the GPU surface; the `attach_surface` flow re-runs the moment the MTKView returns to the window hierarchy; the user sees the last-rendered frame as the static image until the new surface is attached + first `draw_frame` completes (sub-frame latency on modern hardware).
- **Rust `panic = "abort"` triggered inside a UniFFI call** — per `docs/architecture/overview.md` §Workspace Cargo profile, the process aborts cleanly; iOS produces a crash log pointing at the Rust panic site; the user's TestFlight feedback flow surfaces it. No UB; no silent state corruption.
- **App killed mid-`pushBundle`** — Swift has already written shard bytes to `Library/Caches/artifacts/<version_label>/<relative_path>` before calling `pushBundle`; the manifest is written last; on next launch, if the manifest is present and all shards verify, the cache hit fires and the cached live bundle renders; if the manifest is missing (the kill happened before manifest persist), the cache miss fires and the live fetch reruns. No corruption; the manifest's presence is the commit point.
- **iOS 18 device hits a wgpu Metal codepath the version pinned in `shared/` doesn't support** — unlikely (Metal feature levels at the A14 / A15 baseline are uniformly modern per `client-ios.md` §GPU baseline) but if it happens, `EaforaCore::new` returns an error; Swift catches; the app surfaces a "this device is not supported" message panel and stays on the static page shell. No fallback / no degraded mode.
- **App opened via a Universal Link to a region the embedded bundle doesn't know about** (e.g. a future subnational region added in v2+ that's only in the live bundle) — the embedded bundle's `shared::canonical::region_by_code(...)` returns `None`; the region detail sheet presents with a "loading" panel; once the live bundle hot-swap completes, the sheet re-renders with the region's data.

## Requirements *(mandatory)*

### Functional Requirements

#### Xcode project + xcframework build pipeline

- **FR-001**: System MUST add an `ios/` directory at the workspace root structured per `docs/architecture/client-ios.md` §Workspace placement: `project.yml` (XcodeGen config; committed); `Eafora.xcodeproj/` (gitignored; regenerated by `xcodegen generate`); `EaforaApp/` (Swift sources, organized by feature with PascalCase directory names: `Map/`, `Region/`; single-file features flat under `EaforaApp/`); `EaforaApp/Resources/embedded_artifacts/` (gitignored; populated by `scripts/build/sync-embedded-bundle.sh`); `EaforaAppTests/` (XCTest unit tests); `EaforaAppUITests/` (deferred per `client-ios.md` §Testing strategy — the directory may not exist in v1); `README.md` (iOS-development quickstart).
- **FR-002**: System MUST commit `ios/project.yml` per the reference shape in `client-ios.md` §Xcode integration: `name: Eafora`; `options.bundleIdPrefix: org.eafora`; `options.deploymentTarget.iOS: "18.0"`; one `targets.Eafora` of `type: application, platform: iOS`; dependencies `[../target/uniffi/EaforaCore.xcframework, sdk: MetalKit.framework, sdk: Metal.framework]`; pre-build scripts in order (xcframework build → embedded bundle sync → revision injection); code-signing style automatic for Debug, manual for Release; `DEVELOPMENT_TEAM` set to the Apple-assigned 10-character team identifier (not a secret; committed directly).
- **FR-003**: System MUST provide `scripts/build/build-ios-xcframework.sh` per `client-ios.md` §xcframework build pipeline. The script runs the four-step build flow (cargo build for device slice; cargo build for simulator slice; three separate `uniffi-bindgen-swift` invocations producing `--swift-sources`, `--headers`, `--xcframework --modulemap`; `xcodebuild -create-xcframework` combining the slices) and produces `target/uniffi/EaforaCore.xcframework` from source. The xcframework is gitignored. The script is invoked as the first Xcode Run Script pre-build phase (so opening the project in Xcode and building rebuilds the xcframework if Rust source has changed) and explicitly in CI before `xcodebuild build`.
- **FR-004**: System MUST define a `uniffi-bindgen-swift` workspace `[[bin]]` target whose `fn main()` calls `uniffi::uniffi_bindgen_swift()` per `client-ios.md` §xcframework build pipeline. Invoked via `cargo run -p uniffi-bindgen-swift -- ...` in `scripts/build/build-ios-xcframework.sh`.
- **FR-005**: System MUST add `aarch64-apple-ios` and `aarch64-apple-ios-sim` to the workspace's required Rust targets (installed by `setup.sh` via `rustup target add`). The `armv7-apple-ios` target MUST NOT be required (no 32-bit ARM at the iOS 18 baseline per `client-ios.md` §Build profile / overview §iOS client).
- **FR-006**: System MUST extend `setup.sh` to install the iOS-side toolchain dependencies on macOS hosts: `xcode-select --install` (idempotent check), `brew install xcodegen yq` (idempotent), `rustup target add aarch64-apple-ios aarch64-apple-ios-sim` (idempotent), and run `xcodegen generate` in `ios/` to materialize the initial `Eafora.xcodeproj/`. `setup.sh` does NOT compile or build per `client-ios.md` §Xcode integration; the first build happens via Xcode's Run Script pre-build phase.
- **FR-007**: System MUST extend `setup.sh` to run `ios/setup.sh` (which renders the AASA file template into `tools/aasa-deploy/build/` using `yq` to read `TEAM_ID` and `BUNDLE_ID` from `ios/project.yml` — per `client-ios.md` §Rendering the AASA file). Rerunning the script is idempotent.

#### UniFFI surface

- **FR-008**: System MUST add a `shared/src/ffi/uniffi.rs` module per `docs/architecture/client-ios.md` §UniFFI: proc-macro form, dedicated FFI module + `docs/architecture/overview.md` §UDL vs proc-macro for UniFFI. The module exposes an `EaforaCore` UniFFI Object with the FFI surface in `client-ios.md` §UniFFI surface (constructor `new(artifact_path: String)`; `attach_surface(handle: WindowHandle, width, height)`; `detach_surface()`; `resize_surface(width, height)`; `draw_frame(viewport, frame_state)`; `region_at_point(viewport, point) -> Option<RegionCode>`; `async fn push_bundle(manifest_path: String)`; `revision() -> String`). Generic types and trait objects MUST NOT appear in the FFI surface.
- **FR-009**: System MUST define `WindowHandle` as a UniFFI enum per `client-ios.md` §UniFFI: proc-macro form with two variants — `UiKit { layer_ptr: u64, view_ptr: u64 }` for iOS, `AndroidNdk { native_window_ptr: u64 }` for Android. The same `attach_surface` method serves both platforms; the platform-specific data lives in the value the shell constructs, not in the FFI signature. Rust internally converts the variant to `raw-window-handle`'s `RawWindowHandle` for wgpu's surface constructor.
- **FR-010**: System MUST define `AppError` as a single-variant UniFFI Error carrying `message: String` per `client-ios.md` §UniFFI: proc-macro form and the project's error-strings-over-enums preference (`feedback_error_strings_not_enums`). Callers that need to branch on failure mode (e.g. quota-exceeded vs. opfs-unsupported on the web side) match on a documented message prefix. Swift `do` / `try` / `catch` is the call-site idiom.
- **FR-011**: System MUST implement `eafora.revision() -> String` per `client-ios.md` §Core FFI (runtime surface). The Rust core captures the revision at compile time via `shared/build.rs` (running `git rev-parse HEAD` and emitting `cargo:rustc-env=EAFORA_REVISION=...`); `shared::REVISION` is `env!("EAFORA_REVISION")`; the UniFFI surface re-exports as a top-level function. The Swift-side bindings expose this as `eafora.revision()`.

#### Embedded bundle loader

- **FR-012**: System MUST provide `ios/EaforaApp/EmbeddedBundle.swift` per `client-ios.md` §Embedded bundle: app bundle Resources. The Swift type locates the bundled artifact root via `Bundle.main.url(forResource: "embedded_artifacts", withExtension: nil)`, returns the absolute path, and hands it to `EaforaCore(artifactPath:)` synchronously before the first frame.
- **FR-013**: System MUST run `scripts/build/sync-embedded-bundle.sh ${SRCROOT}/EaforaApp/Resources/embedded_artifacts/` as the second Xcode Run Script pre-build phase per `client-ios.md` §Build dependency direction. Same script as web, different argument. Plain `cp -R`; no symlink, no hard link, no rsync. The directory is gitignored.
- **FR-014**: System MUST include `EaforaApp/Resources/embedded_artifacts/` in the "Copy Bundle Resources" build phase so the artifact set is bundled into the `.app` at build time, addressable by `Bundle.main`.

#### Rendering: MTKView + wgpu Metal

- **FR-015**: System MUST implement the MTKView ↔ wgpu surface bridge per `client-ios.md` §Rendering: MTKView + wgpu Metal in three Swift files: `MapView.swift` (SwiftUI container), `MapMTKView.swift` (`UIViewRepresentable` wrapping `MTKView`), `MapRenderer.swift` (`MTKViewDelegate` implementation; owns the `EaforaCore` instance reference; handles the attach / resize / draw / detach lifecycle).
- **FR-016**: System MUST attach the wgpu surface exactly once when the MTKView's `CAMetalLayer` becomes available per `client-ios.md` §Rendering: MTKView + wgpu Metal step 3: `MapRenderer` calls `eaforaCore.attachSurface(handle: .uiKit(layerPtr: ..., viewPtr: ...), width: ..., height: ...)`. Detach (`detachSurface()`) happens when the view leaves the hierarchy (view teardown, scene phase change). Resize (`resizeSurface(width, height)`) happens in `mtkView(_:drawableSizeWillChange:)`.
- **FR-017**: System MUST drive rendering event-driven per `client-ios.md` §Rendering: MTKView + wgpu Metal: `MTKView.isPaused = true`; `setNeedsDisplay()` on every state change (selection, hover, statistic-picker swap, year-scrubber drag, bundle hot-swap). There MUST NOT be a continuous render loop while the scene is idle; the GPU MUST be idle when nothing is happening.
- **FR-018**: System MUST honor `docs/design/README.md` §Animation through v1: state changes are instant; SwiftUI's `.animation()` / `withAnimation` modifiers MUST NOT be used in v1. Future v2+ animations follow the crispness-over-smoothness rule (under 150ms, linear easing, snap-don't-glide).

#### Cache: `Library/Caches/`

- **FR-019**: System MUST implement `ios/EaforaApp/FileSystemArtifactCache.swift` satisfying the `ArtifactCache` Swift protocol per `client-ios.md` §Implementation: `FileSystemArtifactCache.swift`. Required functions: `put(versionLabel:fileRelativePath:bytes:) async throws`, `get(versionLabel:fileRelativePath:) async throws -> Data?`, `listVersions() async throws -> [String]`, `deleteVersion(versionLabel:) async throws`.
- **FR-020**: System MUST store files at `<app-sandbox>/Library/Caches/artifacts/<version_label>/<file_relative_path>` per `client-ios.md` §Directory layout. The directory shape mirrors the OPFS / R2 layout one-to-one; `cache.get(version, "<relative_path>")` resolves to `<base>/artifacts/<version>/<relative_path>` regardless of how the producer organizes subdirectories.
- **FR-021**: System MUST set `NSURLIsExcludedFromBackupKey = true` on the `artifacts/` directory at first creation per `client-ios.md` §iOS-specific behavior. Cache contents are reproducible from the CDN and don't belong in iCloud / iTunes backup.
- **FR-022**: System MUST treat directory creation as idempotent: the cache constructor MUST succeed whether or not `Library/Caches/artifacts/` already exists; the directory is created on demand (covers the iOS-purge-then-relaunch case).
- **FR-023**: System MUST implement `evictOldVersions()` per `client-ios.md` §Implementation: `FileSystemArtifactCache.swift`, called at app launch after the cache initializes. Enumerates version subdirectories, picks the two most recent by `<version_label>` lexicographic order (the `YYYY-MM-DD+<surname>` shape sorts correctly), deletes the rest.
- **FR-024**: System MUST NOT implement any quota / `persist()` machinery per `client-ios.md` §iOS-specific behavior: iOS does not expose a per-app quota; the cache writes until disk pressure forces a purge; the loader's existing first-launch path covers the purge-recovery case.

#### URLSession fetch adapter

- **FR-025**: System MUST implement `ios/EaforaApp/URLSessionFetcher.swift` per `client-ios.md` §URLSession fetch adapter. Surface: `func fetchManifest() async throws -> Data` and `func fetchArtifactFile(versionLabel:relativePath:) async throws -> Data`. Both delegate to `URLSession` (configured with `httpMaximumConnectionsPerHost = 4` to match `client.md` §Stage 3 native-platform cap).
- **FR-026**: System MUST resolve `repositoryBaseURL` at runtime via the discovery URL flow per `client.md` §Discovery and live bundle resolution: the app fetches `https://eafora.org/discovery`, reads `repository_base_url` from the response, and uses that for every shard fetch. A baked-in fallback (populated at build time by a small script that reads the current discovery doc and writes the value into a generated Swift constant) handles the case where discovery itself fails.
- **FR-027**: System MUST implement the speculative parallel fetch at startup per `client.md` §Speculative parallel fetch at startup: discovery fetch + manifest fetch against the baked-in URL fire in parallel; reconciliation per the decision-tree in that section. Speculative-fetch errors are silenced ONLY while discovery is still in flight; once the authoritative URL is known, errors surface normally.
- **FR-028**: System MUST persist verified bytes into `Library/Caches/artifacts/<version_label>/<relative_path>` as each shard's bytes verify against the manifest's SHA-256 entries per `client.md` §Speculative parallel fetch at startup. The cache is keyed by `version_label`; bytes that match a manifest's hashes are correct bytes for that version regardless of which URL served them.

Swift MUST NOT pass bundle bytes across the FFI; the manifest path is the handoff. SHA-256 verification happens inside Rust (`shared::hashing`); Swift MUST NOT duplicate it. Verification mismatch returns an error; Swift handles retry per the loader's retry policy.

### Key Entities

- **`EaforaCore`** (UniFFI Object in `shared::ffi::uniffi`): the opaque handle the Swift app constructs once per app launch via `EaforaCore(artifactPath:)`. Owns the wgpu device + queue + pipeline state (created at construction time, lives until the app exits); the wgpu surface (attached lazily by `attach_surface` when the MTKView's layer becomes available, dropped by `detach_surface` when the view leaves the hierarchy); the renderer's `tokio::sync::watch::Sender<Arc<Bundle>>` (publishes hot-swapped bundles to the renderer).
- **`WindowHandle`** (UniFFI Enum): platform-agnostic surface-attach payload. `UiKit { layer_ptr: u64, view_ptr: u64 }` on iOS; `AndroidNdk { native_window_ptr: u64 }` on Android. Same `attach_surface` FFI method serves both platforms.
- **`AppError`** (UniFFI Error): single-variant `GenericError { message: String }` per the project's error-strings preference. Swift sees this as a `throws` error; callers that need to branch on failure mode match on a documented message prefix.
- **`FileSystemArtifactCache`** (Swift class in `ios/EaforaApp/FileSystemArtifactCache.swift`): implements the iOS side of the cross-platform `ArtifactCache` contract. Wraps `FileManager` operations against `<app-sandbox>/Library/Caches/artifacts/`. Stateless — every call resolves the directory on demand; the constructor creates the directory if missing and sets `NSURLIsExcludedFromBackupKey`.
- **`URLSessionFetcher`** (Swift class in `ios/EaforaApp/URLSessionFetcher.swift`): the iOS side of the cross-platform fetch adapter contract. Wraps `URLSession.shared` configured with `httpMaximumConnectionsPerHost = 4`. The retry policy lives Rust-side in `shared::artifact`'s loader; the Swift fetcher just propagates errors.
- **`EmbeddedBundle`** (Swift namespace in `ios/EaforaApp/EmbeddedBundle.swift`): locates the bundled artifact root via `Bundle.main.url(forResource: "embedded_artifacts", withExtension: nil)` and hands its path to `EaforaCore(artifactPath:)`. Synchronous; runs before the first frame.
- **`MapView` / `MapMTKView` / `MapRenderer`** (Swift in `ios/EaforaApp/Map/`): the SwiftUI map surface bridge. `MapView` is the SwiftUI container; `MapMTKView` is the `UIViewRepresentable` wrapping `MTKView`; `MapRenderer` is the `MTKViewDelegate` that owns the `EaforaCore` reference and drives the attach / resize / draw / detach lifecycle.
- **`RegionCode`** (Swift struct in `ios/EaforaApp/Region/`): wraps the `region.code` string; conforms to `Identifiable` + `Hashable` for `.sheet(item:)`. Distinct from any UniFFI-generated `RegionCode` (which is the FFI surface form).
- **`AASA file` at `https://eafora.org/.well-known/apple-app-site-association`**: rendered from `tools/aasa-deploy/apple-app-site-association.template.json` with `TEAM_ID` and `BUNDLE_ID` injected from `ios/project.yml`; served by the dedicated assets-only `tools/aasa-deploy/` Cloudflare Worker; deployed by `scripts/build/deploy-aasa.sh`. Declares `appID` and the deep-link paths `/region/*` and `/about`.

## Assumptions

- The `shared/` crate exists and exposes the consumer surface documented in `client.md` §Module layout, which it now does: `shared::artifact::Bundle`, `shared::artifact::manifest::parse_manifest`, `shared::filesystem::verify_sha256`, `shared::map::map_renderer::Renderer`, `shared::map::WgpuSurface`, `shared::license::DistributionContext`. Landed with `005-core-data`, `006-core-renderer`, and the web client, all on `master`. What does **not** exist is the FFI boundary this feature needs: there is no `shared/src/ffi/`, no `uniffi` dependency in the workspace, and no `uniffi-bindgen-swift` binary. Standing that up is the first phase of this feature rather than a prerequisite of it, since it is Rust work that builds and tests without Xcode.
- The producer-side `ingestion build --downsampled <output-dir>` exists. Same dependency as 003-web-client (FR-004 there); `scripts/build/sync-embedded-bundle.sh` (registered in the 003-web-client feature) is reused verbatim with a different argument.
- The producer side has NOT necessarily stood up `repository.eafora.org` or the `latest/manifest.json` upload step at the moment this feature's PR opens. Until those land, the live-fetch path (P3) is exercised against a same-origin stub committed under `ios/EaforaApp/Resources/embedded_artifacts/` plus the discovery document shipped by the 003-web-client feature.
- **There is no Apple Developer Program enrollment yet**, confirmed by `security find-identity -p codesigning -v` reporting zero valid identities. This is not a blocker for most of the feature: the simulator needs no signing, so the app, the renderer, the cache, and the live-fetch path are all buildable and testable without it. It hard-gates only device installs, TestFlight, App Store distribution, and Universal Links, since an AASA file has to declare a real `appID` and a device has to run a build claiming `applinks:eafora.org`. Those are confined to the last phase for that reason.
- The build host has Xcode installed, which it does: Xcode 26.5 (build 17F42), comfortably past the iOS 18 SDK the design assumed. Three things are **not** in place and each blocks a specific phase rather than the feature as a whole: no iOS simulator runtime is installed (`xcrun simctl list runtimes` is empty), so nothing can run on the simulator until one is; the `aarch64-apple-ios` and `aarch64-apple-ios-sim` Rust targets are not installed; and `xcodegen` is absent, though `yq` v4.52.5 is present. `setup.sh` gains these.
- `uniffi-bindgen-swift`'s per-artifact invocation pattern (separate `--swift-sources`, `--headers`, `--xcframework --modulemap` calls) is current as of UniFFI 0.29+ (`client-ios.md` §Things to verify #1). If the pattern has shifted, `scripts/build/build-ios-xcframework.sh` adapts accordingly.
- The wgpu Metal-from-`CAMetalLayer` API name is stable in the version pinned in `shared/`'s Cargo.toml (`client-ios.md` §Things to verify #2). If the name has shifted, the surface-construction code in `shared::ffi::uniffi`'s `attach_surface` adapts.
- The XcodeGen YAML schema referenced in `client-ios.md` §Xcode integration matches the XcodeGen version installed by `setup.sh`. The schema has been stable for years but is worth a spot-check against the installed version.
- `MTKView.isPaused = true` + `setNeedsDisplay()` semantics drive an on-demand-only render loop without periodic GPU wakeups (`client-ios.md` §Things to verify #3). If the combination doesn't behave as expected on iOS 18+, the renderer adapts to use `MTKView.preferredFramesPerSecond` differently — but this is the documented Apple pattern, so the spec assumes it works.
- `xcodebuild -exportArchive` with `destination = upload` in `ExportOptions.plist` and the `-authenticationKey*` flags performs the App Store Connect upload directly without a separate `altool` step (`client-ios.md` §Things to verify #5). Fallback if it doesn't work: separate `xcodebuild -exportArchive` (export only) + `xcrun altool --upload-package`, even though `altool` is deprecated.
- The AASA Worker's route pattern (`eafora.org/.well-known/apple-app-site-association`) takes precedence over the main web Worker's catch-all route on Cloudflare (`client-ios.md` §Things to verify #6). Verifiable after the first deploy; not a code change either way.
- The Universal Link domain (`eafora.org`) is registered through Cloudflare per the project memory `project_eafora_domain`; routing it to the AASA Worker is a dashboard / `wrangler.toml` configuration step, not a code dependency.

## Phasing and planning depth

This feature is the scale of everything phases 0a through E delivered for the web client, so it ships in phases, each its own PR. The plan carries **implementation detail for phases 0 through B only**. Phases C and D are sketched: their scope is fixed here, but the task breakdown is deliberately absent and has to be written before either is picked up.

- **Phase 0 — the FFI boundary.** `shared/src/ffi/`, the `uniffi-bindgen-swift` binary, and `scripts/build/build-ios-xcframework.sh`. Pure Rust and shell: it builds, tests, and reviews on any machine, with no Xcode project and no simulator. Planned in detail.
- **Phase A — the app renders.** `ios/` scaffolding via XcodeGen, the app skeleton, the embedded-bundle loader, the `MTKView` bridge, and first paint on the simulator. Needs a simulator runtime installed. Planned in detail.
- **Phase B — data over time.** The file-system cache adapter, discovery, the speculative fetch, and the bundle hot-swap. Planned in detail.
- **Phase C — the rest of the surface.** Region detail, settings, the About content, and `DesignTokens.swift`. **Sketch only: needs a task breakdown before it is picked up.** It depends on nothing outside this repository, so it can be planned whenever.
- **Phase D — distribution.** Universal Links, the AASA worker, and the TestFlight pipeline. **Sketch only: needs a task breakdown before it is picked up, and cannot be planned in detail until the Apple Developer Program enrollment exists**, because the signing identity, the `appID` in the AASA file, and the App Store Connect API key are all inputs to the steps rather than outputs of them.

A phase marked sketch-only is not a lighter phase; it is an unplanned one. Picking one up starts by writing its tasks.

## Constitution Check

Per Constitution §Compliance review, this spec honors the binding principles as follows:

- **Principle I (Educational neutrality)**: directly served. The iOS app's UI text is limited to labels, units, source attribution, and statistic definitions; the About content in Settings is etymological + framing (per `docs/design/README.md` §Naming and the About page), explicitly factual rather than advocacy. No editorial copy in v1.
- **Principle II (Source provenance — NON-NEGOTIABLE)**: applies. The region detail sheet exposes per-cell source attribution (the same `shared::*` queries the web shell uses, against the same SQLite shards); the Settings sheet's future Data sources section will surface the `source_revisions` block from the active bundle's manifest. Every datum the user sees in the app traces back through the producer-side merge step's `data_source_id` lineage.
- **Principle III (Rust core, native UI shells)**: directly served. The iOS shell is SwiftUI + Metal (per `client-ios.md`); the Rust core (`shared/`) handles manifest parsing, SQLite queries, FlatGeobuf reading, hit-testing, projection math, and the wgpu rendering pipeline (which targets Metal on iOS). The Swift layer is thin per the "1–2k LOC per-platform layer" target in `client.md` §Cross-platform consistency.
- **Principle IV (Singularity convention parity)**: applies. The iOS work introduces no new third-party Rust crates (UniFFI is already implied by `shared/`'s FFI module); the Swift dependencies (the iOS SDK frameworks `MetalKit`, `Metal`) are platform-provided, not third-party libraries. XcodeGen (`brew install xcodegen`) and `yq` (`brew install yq`) are new tooling installed by `setup.sh`; both are mainstream tools whose adoption follows the "discuss before adopting" rule trivially (XcodeGen is the documented choice in `client-ios.md`; `yq` is the YAML-querying tool the AASA-render script needs). The `uniffi-bindgen-swift` workspace `[[bin]]` is a tiny wrapper, not a new dependency.
- **Principle V (Explicit over implicit)**: applies. The iOS app doesn't host HTTP routes (no actix-web); the `URLSessionFetcher` calls `URLSession.shared` directly (the wire is visible at the call site). No RPC framework, no Swift-side code-generation that hides HTTP. UniFFI is code-generated, but per `client-ios.md` §UDL vs proc-macro for UniFFI it's explicitly allowed: the FFI surface is the only viable codegen path, and the discipline of `shared/src/ffi/uniffi.rs` as the single reviewable surface preserves the "see the wire" property at the right granularity. Imperative navigation in `EaforaApp.swift` (explicit `.sheet` bindings driven by `@State`); no `NavigationStack` push for the About inlining decision.
- **Principle VI (CDN-delivered data, no live API through v2)**: directly served. The iOS client consumes only the manifest + shards served from the static CDN (`repository.eafora.org`) and the static discovery document at `eafora.org/discovery`. No origin-server calls; no live API; no v3+ surface. The AASA file is also a static asset.
- **Principle VII (Test-first for core logic)**: applies to the iOS-side helpers per `client-ios.md` §Testing strategy. `FileSystemArtifactCache`, `URLSessionFetcher` error mapping, MTKView ↔ Rust bridge, `EmbeddedBundle.swift`, and Universal Link routing each have XCTest unit tests.
